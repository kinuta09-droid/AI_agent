# Process Lifecycle & Windows Process Management

- **Bot/Scheduler duplicate processes -> always acquire via `lib.pid_guard.acquire()`**. Never hand-roll a "check PID file then write it" guard: the two steps are not atomic, so processes starting within seconds of each other (heavy imports run *before* the guard) all decide "no live instance" and all write the lock. This let a 2nd Discord bot connect to the gateway, so one `/agent` ran twice in parallel and `logs/skill_observations.jsonl` got same-second duplicate entries (2026-07-17)
- Duplicate entries in `logs/skill_observations.jsonl` are **not** a nested-wrapper bug: `observe()` has exactly one call site (`engine_plan_execute.py`) and the registry stores raw callables. Same-second entries with *different* args = two concurrent processes, so count the processes first (`Get-CimInstance Win32_Process`, check who holds the Discord socket)
- PID は再起動をまたいで一意ではない。電源断で残った PID ファイルの PID が次のブートで再利用されていると `is_process_alive` が(安全側に倒れて)「生存」と答え、`acquire()` が永久に False -> Bot が無言で起動しない。`main.py` は即 exit を 5秒毎に再起動するだけで heartbeat 判定に到達しないため通知も出ない。**PID と一緒にブート ID を記録**して前ブートの残骸を無条件 stale にする (`lib/pid_guard.boot_id`)
- heartbeat が守るのは「上がったプロセスが止まったか」だけ。「そもそも上がってこない」は守備範囲外 -> `lib/watchdog.is_fast_exit` / `restart_delay` / `should_alert` で crash loop を検知・通知する。PC 起動時に立ち上がらないときの確認順は `scripts/AUTOSTART.md`
- PC再起動後にBotが無言で起動しない事象を追ったら、`Get-ScheduledTask` で `ARMS Launcher` タスク自体が未登録だった。`scripts/AUTOSTART.md` の `schtasks /create` は手動一回限りの手順で git 管理外のため、コード側をどれだけ直しても `main.py` が一度も走らなければ無意味。新しいマシン/ユーザーでのセットアップでは必ず `schtasks /query /tn "ARMS Launcher"` で登録有無を先に確認する
- Windows `os.kill(pid, SIGTERM)` throws `OSError [WinError 87]` for dead PIDs -> catch `OSError`
- `os.kill` は CPython 内部で `OpenProcess(PROCESS_ALL_ACCESS)` を要求する。タスクスケジューラが `/rl highest` で起動した高整合性プロセスを非管理者プロセス (`scripts/arms_ctl.py` 等) から終了させようとすると `PermissionError [WinError 5]` になる。**終了そのものに使える権限は `PROCESS_TERMINATE` だけで足りる**(同一ユーザーなら整合性レベルをまたいでも DACL で許可される)。`OpenProcess(PROCESS_ALL_ACCESS)` という過剰な権限を要求しているせいで失敗しているだけなので -> `lib/watchdog._terminate_via_handle` にフォールバックする
- `OpenProcess` failing does **not** mean the process is dead: `ERROR_ACCESS_DENIED(5)` = alive but not queryable. Treating it as dead re-opens the duplicate-startup hole -> fall back to "alive" when in doubt (see `lib/pid_guard.is_process_alive`)
- WMI `CommandLine LIKE '%foo%'` matches **your own query process** -> filter on `Name = 'python.exe'` before believing a stray process exists
- **「取りこぼし対策」を一部のジョブにだけ入れると、対象外のジョブで同じ事故がそのまま再発する** (2026-08-12)。2026-08-12朝、Daily Note (07:00) / Morning Briefing (07:30) / Daily News (08:00) など日次生成系ジョブが一つも走らなかった。真因は三段: (a) `run_scheduler` のメインループは `current_time == task["time"]` の完全一致の分でしか発火せず、その分にプロセスが不在なら永久にスキップ、(b) 既存の `_run_catch_up()` は `if weekday is None: continue` と書かれており **週次ジョブ専用** で日次ジョブは最初から対象外、(c) `ARMS Launcher` タスクのトリガーが `BootTrigger` ではなく `LogonTrigger` のため、Windows Update の無人再起動 (05:00) 後 12:05 のログオンまで7時間 ARMS 自体が不在だった (`scheduler.log` は 04:45:04→12:05:21 まで無記録)。**週次ジョブには catch-up の成功体験が既にあった** (08-10 に実際に週次ジョブが catch-up 発火している) ため、「日次にも同じ仕組みが効いているはず」という誤認が生まれ、対象外である事実がそのまま放置されていた。部分的な対策は「対策済みだ」という誤った安心を生む。対処: `_last_scheduled_occurrence()` に `weekday=None` (=直近の HH:MM) を追加し `_run_catch_up` の weekday 必須を撤廃、朝の生成系7本に `catch_up=True` を付与。**ただし相場系 (BTC Analysis / Crypto Market Scan / Crypto Sweep) には意図的に付けていない** — 遅れて実行すると古い値動きを「今の分析」として出すだけで、生成されない方がマシ。「取りこぼしたら後で実行する」は常に正ではなく、鮮度が価値の本体のジョブでは catch-up は害になる。回帰は `tests/test_scheduler_catch_up.py` [1]〜[5] ([5b] は相場系に `catch_up` が付いていないことを検査)。`LogonTrigger` の `BootTrigger` 化自体は未対処 (システム設定変更のためユーザー確認待ち) — PC起動中でも未ログオンの間は ARMS が一切動かない状態は残っている
- **並列実行を逐次実行に変えると、二重発火と失敗の隔離喪失という別種のバグが同時に生まれる** (2026-08-12、上の catch-up 対応の直後)。朝の連鎖 (XTrend 06:00 → Auto Deep-Dive 06:30 → Morning Briefing 07:30) は前段の出力を後段が読むため、catch-up の発火を「1ジョブ1スレッドの並列」から「予定時刻順の逐次1スレッド」に変更した。この変更が新たに2つの穴を開けた。(a) 二重実行: `run_scheduler` は `last_run_minute=""` で始まりメインループの1周目が「今の分」のジョブを即発火させる。逐次化により catch-up がキュー後方のジョブへ到達するのは数分後で、その頃には相手のロックは解放済みのため**同じジョブが2回走る**。`_execute_task` の `task["_lock"].acquire(blocking=False)` は「実行中の重なり」しか防げず時間差の二重実行は防げない。実害は Gemini の二重課金と `tool_create_note` の重複名タイムスタンプ退避による Vault のゴミノート。対処: occurrence が現在の分と同じものは catch-up 対象から除外し定時発火に任せる。(b) 失敗の隔離喪失: 1ジョブ1スレッドなら1本落ちても他は走ったが、1スレッド化により `_execute_task` の外側 (開始通知の送信・`_lock` 未初期化) で例外が出ると、**残りの catch-up ジョブが daemon スレッドの死と一緒に無言で消える** (`_execute_task` は `task["func"]()` の例外は自分で捕まえるが、逐次ループ本体には except が無かった)。対処: 逐次ループ本体を try/except で囲みログを残す。両方とも自己レビュー (grill 相当) で実装直後に検出・修正。回帰は同ファイル [7][8]、修正を外すと [7a] は `ran=['PastJob','NowJob']` の重複、[8] は `ran=[]` の消失で赤くなることを確認済み
- **タスクスケジューラの `ExecutionTimeLimit` は最上位プロセスしか殺さない。子プロセスは孤児のまま生き残り、次回発火のたびに1体ずつ増える** (2026-08-29、AI_agent 本体とは無関係な個人スクリプト `~\.local\bin\hyperframes-preview-reaper.ps1` — git管理外だが Windows Task Scheduler の一般教訓としてここに記録)。症状: `npm exec hyperframes preview --list --json` に相当する `node.exe` プロセスが2時間おきに1個ずつ増え続け、`tasklist` を見るたびに数が伸びていた。真因: 2時間毎起動のタスクが `powershell.exe → cmd.exe → npx.cmd → node.exe` の子孫プロセスを `&` 呼び出し演算子(`Start-Process` を介さない素の呼び出し)で起動しており、タスク定義の `ExecutionTimeLimit=PT5M` は**トップレベルの `powershell.exe` だけ**を5分で強制終了する。`node.exe` 側がネットワーク越しの `npm registry` 最新版チェック等で稀に5分を超えて詰まると、`powershell.exe` は消えるのに子孫プロセスツリーは孤児化して生き残り、`MultipleInstances=IgnoreNew` はタスク自体の二重起動しか防がないため次の発火はまた新しい孤児を1個追加するだけ、という無限蓄積になる。`Get-ScheduledTaskInfo` の `LastTaskResult` だけを見ても「時間切れで打ち切られた」ようにしか見えず、孤児化には気付けない — 実際に `wmic process ... get ParentProcessId` で親を辿り、親PIDが「インスタンスなし」(既に終了済み) なのに子が生きていることを確認して初めて発覚した。対処: 呼び出し側を `Start-Process -PassThru` に変え自前で `WaitForExit(timeoutMs)` し、タイムアウト時は `taskkill /T /F /PID <pid>` で**プロセスツリーごと**終了させる (`Stop-Process` は対象PIDのみで子孫は道連れにならない点に注意)。**一般化**: `ExecutionTimeLimit` やタイムアウト付きラッパーに「子プロセスを生む可能性のあるコマンド」(`npx`/`npm`/シェル経由の外部ツール呼び出し全般) を渡すときは、素の `&`/`Start-Process -Wait` ではなく必ず `taskkill /T` (Windows) 相当のツリーキルを自前で持たせる。AI_agent 本体の `scripts/arms_ctl.py` 等が将来 `ExecutionTimeLimit` 付きタスクを新設する際も同じ穴を踏みうる
- **実行中プロセスを `__main__` として動かすファイルを、tools 側から名前で `import` すると、同じファイルがもう一度先頭から実行され二重初期化する** (2026-08-11)。`scheduler.log` とコンソール出力が2026-08-11 03:20 を境に全行2重になった。プロセスは1つしか無い (launcher・`Starting scheduler` ログとも1回だけ) ため「多重起動」と誤読しかけたが、真因は `tools/tool_vault_watcher.py` の `_default_notify()` が実行時に `from agent_scheduler import send_discord_notification` していたこと。実プロセスは `agent_scheduler.py` を `__main__` として動かしているため、この import は Python にとって**別モジュール**であり、同じファイルの中身がもう一度先頭から実行される。`logging.getLogger("Scheduler")` は同一シングルトンを返すが、モジュール末尾の `logger.addHandler()` が2度目に走ってハンドラが2組になり、以降の全ログが2重出力される (重い tools 群も再 import される)。対処は**呼び出し側でなく共有側**: `logger.addHandler()` の前に `if not logger.handlers:` ガードを置いた。呼び出し側 (`from agent_scheduler import ...` する箇所) は今後も増えうるので、そのたびに直すより1箇所のガードの方が小さい差分。回帰は同ファイル [6] が `importlib.reload` 後にハンドラ数が増えないことを検査、ガードを外すと `before=2 after=4` で赤くなることを確認済み
