# Retrieval, Reranking & Tool-Selection Tuning

## リランク / ローカルLLM実行

- **ローカルLLMが遅いとき、まず疑うのは推論ではなくモデルの再ロード**。リランクを Ollama へ移した際、候補20→10・スニペット600→300字と入力を半分にしても 15.25→14.11秒 にしかならなかった。切り分けると「リランク連続 6.75秒 / 埋め込みと交互 10.68秒」で **計算時間 (prompt_eval_duration) は 3.93秒で同一** = 差は全部ロード。`/api/ps` を見ると VRAM 6GB に bge-m3 (1.16GB) と qwen2.5-coder:7b (4.68GB) が同居できず、検索のたびに追い出し合っていた (`keep_alive` は入りきらないので無効)。**クエリ埋め込みだけ CPU (`options.num_gpu=0`) に逃がす**と共存して 16.2秒 → 6.0秒 (クエリ1本なら CPU で 2.3秒)。インデックス構築 (数千チャンクのバッチ) は GPU のまま — この分離は `tests/test_rerank_backend.py` が ast で呼び出し元を静的検査する。切り分けには Ollama 応答の `prompt_eval_duration` / `eval_duration` / `eval_count` を見る
- **「同時に切り替えないと黙って劣化する」2つの設定は、既定を auto にして追従させる**。リランクのバックエンド (gemini/ollama) とクエリ埋め込みのデバイス (gpu/cpu) は揃っている必要があり、片方だけ変えると**動きはするが7秒遅くなる**。独立した env 2本にすると片方だけ変えた事故に気付けないので、`VAULT_QUERY_EMBED_DEVICE` の既定を `auto` にしてバックエンドから導出する (明示指定は上書き可)。回帰は両方向を固定する
- **ローカルモデルは「速いから小さいのを選ぶ」が通用しない**。qwen3:1.7b はリランクで MRR@10 0.6244 と**リランク無し (0.7317) すら下回った** — 小さすぎて候補本文を読めておらず、順位を積極的に壊す。一方 qwen2.5-coder:7b は 0.8722 で Gemini (0.8167) を上回った。**「LLMを噛ませた」こと自体は改善を意味しない**ので、必ずリランク無しのベースラインと比べる
- **GPU常駐 (`keep_alive`) は他機能とVRAMを奪い合う**。検索のリランカを常駐させると VRAM 4.09GB を占有し、同じ GPU を使う ComfyUI (`tool_lora_factory`) の画像生成と競合しうる。常駐時間は env で調整可能にし、代償をコードに明記する
- **事前に書いた根拠が実測で否定されたら、コメントを書き換える**。「リランカ常駐中に埋め込みバッチをぶつけると VRAM を奪い合う」と書いてジョブ時刻を決めたが、実測では検索は +0.1秒 (誤差) だった。`/api/ps` を見ると bge-m3 が `size_vram: 0` = CPU 常駐で、クエリ埋め込みを CPU に逃がした結果 Ollama が既存ランナーを再利用していた。つまり **直前に検索があったかどうかでバッチが GPU/CPU どちらで走るかが変わる** (ast 検査は呼び出し側の意図しか守れない)。測って否定された理由を残すと、次に読む人が同じ誤解を引き継ぐ

## 検索順位の安定性

- **同点スコアの順序を不安定ソートに任せない**。`_semantic_hits` が `np.argsort(-scores)` を既定の quicksort で呼んでいたため、**同点チャンクの順序が配列の中身に依存**していた。行動ログ178行を同じテーブルに足したら、無関係なはずの R03 でスコア完全同値 (0.5807) の2ノートが入れ替わり、リランカへ渡す候補の番号が1つずれて最終順位が 4位→7位、hit@5 が 1.0→0.9333 に落ちた。**行が増えただけで既存の順位が動くのは、それ自体が欠陥**。SQL 側の `ORDER BY filepath, chunk_index` と numpy 側の `kind="stable"` は**対で**「行集合に依存しない順序」を作るので、片方だけ消しても落ちるテストを置く (`tests/test_activity_corpus.py` [8])。なお**旧ベースラインの hit@5 1.0 はタイの並び順の運**だった — 数字を戻すためにタイブレークを逆向きにするのは、指標に合わせた調整であって改善ではない

## 計測方法論 (A/B・評価汚染)

- **A/B の「before」は、施策以外が動いていない同じ土俵で取り直す**。回帰ゲートが落ちたとき比較対象は3時間前のベースラインで、その間に Vault インデクサが14ファイルを更新していた。施策の効果と索引の変化が混ざり、`is_clean_arm()` はリランク設定しか見ないので ⛔ も出ない。**同一インデックス上で行動ログの有無だけを変えて測り直す**と順位変化ゼロになり、真因 (不安定ソート) が分離できた。切り分けの順序は「RRF単体 → リランカの再現性 → 候補集合の中身」で、どれが動いたかを見ずにレイヤーを決めつけない
- **「一部にしか施策が効いていない計測」は、集計値だけ見ると改善に見える**。ON アームを15問走らせている途中に Gemini 日次上限(200)へ到達し、10問がフォールバック (=ベースラインと同一結果) になったのに、集計は `hit@5 0.93 → 1.0` と出た。**数字自体は正しいが、施策の効果ではない** (実際に効いたのは5問だけ)。→ `scripts/eval_retrieval.is_clean_arm()` で「ONを要求したのにフォールバックした問があるか」を判定し、**JSONのフラグ・比較表の ⛔ 行・プロセス終了コード2** の3箇所に出す。**計測の汚染は数値と一緒に持ち回る** (別の場所にログを出すだけだと、数値をコピーした時点で剥がれる)。なお日次上限は生活側の利用だけで ~190/200 消費するので、検索1回あたり +2回の施策は上限に当たりやすい
- **難問セットが作れなかったら、問数を水増ししない**。Retriever ループの効果を測るため「1周目で外す難問」を16問用意したが、**全問 hit@5 に入ってしまった** (この Vault では言い換えだけで「見つからない問」を作れない)。無理に難しくすると測っているものが変わる。fixture の `_about` に「当初の意図・実測で何が起きたか・したがってこのセットが測れるのは順位改善だけ」と書き残し、名前と実態の食い違いを潰す
- **どのチェックが落ちたかを見ずに原因のレイヤーを決めつけない**。T12 は plan 側のアサーションが全て pass で `exec_assertions` (回答テキスト) だけが落ちていたのに「Planner のプロンプト問題」と要約されていた。実際の修正箇所は最終要約層で、Planner を触っても一生直らなかった。`logs/eval/*.json` の `checks` / `exec_checks` を必ず開く
- **アサーションを緩めて自分の変更を通していないか、証拠で示す**。同 PR で T12 が一度 fail したが、回答は「ツール一覧に含まれていません」と正しく、`answer_must_match` が否定の言い回しを4種しか列挙していなかっただけ。正規表現を広げる前に**旧バグ回答が広げた後のパターンにも一致しないこと**を確認し、それを固定するテストを置く (`tests/test_answer_grounding.py` の [6] がベースライン JSON を読んで検証する)

- **「ユーザー起点の呼び出しだけを数えたい」ログ/計測を公開関数に新設するとき、その関数を内部で叩いている既存の自動化ジョブを見落とすと自己言及的な水増しが起きる** (2026-08-22、教訓昇格機能)。`tool_vault_hybrid_search()` (Planner/Discordから呼ばれる唯一の公開検索エントリ) に検索ログ (`logs/vault_search_log.jsonl`) への追記を追加したところ、`tools/tool_vault_watcher.py` (夜間に変更ノートを検知し関連ノートを自動検索してGeminiに関係性を判定させる既存機能) の内部検索 (`_default_search` → `tool_vault_hybrid_search`) がそのままこの新ログに素通しで記録される経路になっていた。この機能は「よく参照されるノート」を検出するために人間/エージェントの実際の参照実績を数えることが前提なのに、Vault Insight Watcherが毎晩自動発行する内部検索が混入すると、**自動化ジョブ自身の動作が「よく参照されている」という誤った判定の根拠になる**。同種の内部検索である `tool_find_related_notes` は最初から記録対象外にする設計にしていたが、`tool_vault_watcher.py` 側の経路は見落としていた。修正は `_default_search` に `log_fn=lambda query, hits: None` を渡し、この経路だけ明示的にログ対象から除外。**一般化**: ユーザー起点の呼び出しだけを数えたい/記録したいという前提でログ・カウンタ・メトリクスを新設するときは、その公開関数を grep して**内部で**呼んでいる既存の自動化ジョブ・バックグラウンド処理を全て洗い出し、ユーザー起点かシステム内部起点かを分類してから内部起点の経路だけを明示的にオプトアウトさせる。1箇所だけ対応して他を見落とすと、新設した指標そのものの前提が壊れる (Category C の「本番と共有する可変資源からテストを隔離する」と同系統だが、こちらは本番コード同士の内部呼び出しが計測を汚染するケース)。回帰は `tests/test_vault_watcher.py` の `test_default_search_disables_search_log_write` (`_default_search` が実際に `log_fn` を渡すことを検証。`tests/test_hybrid_search.py`/`tests/test_vault_links.py` は別経路 — 自テストの検索フィクスチャが本番ログを汚染しないための隔離であり、Watcher側の修正そのものは検証していない)

## クエリの形式とインデックス更新タイミング

- **`_keyword_hits` は空白区切りの短いキーワード列専用で、日本語の長文をそのまま渡すと事実上無力化する**。`tool_find_related_notes` (アイデアノートの要約文をqueryにする新機能) 実装時に判明: `tools/tool_obsidian.py:_keyword_hits` は `keywords.split()` でトークン化するが、日本語の1〜3文にはスペースが無いため**文全体が1トークン**になり、キーワード側マッチングは「その一文全体と完全一致する行があるか」相当に潰れて実質0件しか拾えない。`_hybrid_hits` はこの状態でも例外を出さず**意味検索(embedding)側だけが実質的な検索エンジンになって**動いてしまうので気付きにくい。長い自然文をqueryにする新機能を作るときは、事前に主要な名詞句を抽出してキーワード側にも渡すか、キーワード側の寄与が実質ゼロであることを前提に設計する
- **「関連ノートが見つからない」調査は、まず `vault_index.db` の files テーブルに対象が存在するかを見てから、ランキングかしきい値の問題かを切り分ける**。`vault_index.db` は `agent_scheduler.py` の "Vault Semantic Index" ジョブ (毎日03:15、`tools/tool_vault_index.update_vault_index`) でのみ更新され、保存時にリアルタイム反映されない。実機で「同日作成した類似ノート同士が関連候補に出ない」報告があったが、`sqlite3` で `SELECT filepath, mtime FROM files WHERE filepath LIKE '%...%'` を引くと両方ともインデックス済みで、真因は索引未反映ではなく **5位にヒットしていたが `top_k=3` の枠から漏れていただけ**だった。理論上は「当日03:15より後に作成したノートはその日一日ヒットしない」ケースもあり得るので、原因を決め打ちせず filesテーブル確認→順位/しきい値の順で切り分ける

## Vault一括走査ツールの実装パターン

- **Vault内の全 `.md` を一括走査するツールは、1件のファイル読み込み失敗で全体を止めてはいけない**。新規実装した `tools/tool_vault_export.py` の `_read_body()` は単純な `open(..., encoding="utf-8")` で、非UTF-8保存や破損ファイルが1件混じるだけで `UnicodeDecodeError` 等が飛び、実測929件の走査全体が停止する欠陥があった。`/grill` で指摘して気付いたのは、**同じ「Vault全体を舐める」処理である `tools/tool_vault_index.py` (505-513行目・623-626行目) には既に `errors="replace"` (デコード不能バイトは置換文字で読み進める) + `try/except OSError: continue` (該当ファイルだけ諦めて次へ) という確立パターンがあった**にもかかわらず、新規実装時にこれを見落として素朴に再実装してしまったこと。**Vault全走査系の新規ツールを書くときは、まず `tool_vault_index.py` のファイル読み込み部分を先に見て、このパターンをそのまま踏襲する** (車輪の再発明をしない)。修正は `errors="replace"` + `except OSError` で該当ファイルをスキップする形に書き直して対処 (`3650a32`)。回帰テストは未追加 (929件中1件の破損ファイルを人工的に用意するコストが高いため、当面は本節の明文化のみ)。2026-08-16

## ツール説明文とPlanner選択

- **ツール名は実装の識別子であって、ユーザーの語彙ではない**。ツールの実行実績を検索可能な文書にしたとき、`tool_gmail_check` という文字列には「メール」という語が一度も出てこないので「メールを確認する機能がうまく動かなかったことはあるか」に bge-m3 が反応できなかった (評価 A02/A08 が圏外)。`lib/tool_registry.get_tool_descriptions()` の日本語説明を本文に入れて hit@5 0.75→0.875。**説明文だけが欲しい呼び出し側に、callable 解決 (tools/* の全 import) の代償を払わせない**ようアクセサを分ける
- **ツールの `description` は Planner の唯一の選択根拠**。`tool_update_note` が `"追記"` の2文字だった頃、「既存のデイリーノートに追記して」は説明文に「デイリーノート」を含む `tool_sync_to_daily_note` (予定/タスク同期) に語彙一致で奪われていた (eval T09)。守備範囲だけでなく**非対象**も書く。ただし一方に語を足したら他方の縄張りも明示すること — 逆流して今度は同期要求を奪う
- Planner over-relies on `tool_vault_search` -> explicit tool selection guidelines needed
