# AI駆動型ウェブデザイン・量産ワークフロー

出典: ユーザー提供マニュアル「AI駆動型ウェブデザイン・量産プロセス標準化マニュアル」
(`C:\Users\amami\Downloads\AI駆動型ウェブデザイン・量産プロセス標準化マニュアル.md`)

このスキルは案件の進行管理に使う。各フェーズの完了条件を満たさずに次へ進めない。
飛ばしてよいのは Phase 4 (動画背景) のみ — 静的サイトなら省略可。

## 全体の流れ
```
Phase1 リファレンス収集 → Phase2 アセット分離 → Phase3 コード実装 → Phase4 動画背景(任意) → Phase5 仕上げ
   (20-30分)              (Hickfield等)         (Claude/Fable5)      (Luma/Kling)          (人間の審美眼)
```

## Phase 1: リファレンス収集(高認知フェーズ)
目的: 良い出力の8割はここで決まる。単一サイトの模倣ではなく要素合成で独自性を作る。

- [ ] Pinterest / Motion Sites を主軸に **20〜30分** 探索する(時間を厳守。短すぎても長すぎてもダメ)
- [ ] 1つの「完成サイト」を探すのではなく、3要素に **分解して** 別々に集める
  - レイアウト(テキスト配置・ナビゲーション構造・情報の重なり)
  - グラフィックス(核となるオブジェクト。例: 蝶・枝・ふわふわ3D物体・ポータル状のパーティクル演出)
  - カラー/質感(ダークグラデーション・テクスチャ・光の当たり方)
- [ ] Figmaに解像度不問でスクリーンショットを並べ、AI指示用の構成案にする
- [ ] **動画リファレンス(SNS投稿のデモ動画等)も1枚として扱う**: 強く印象に残る動画ほど「これを丸ごと再現したい」に
      引っ張られやすいが、そのサイトを丸ごと模倣すると (a) 上記の要素分解の原則に反する、(b) 他者の具体的な
      実装の複製になりかねない。**演出要素だけを抽出して他のリファレンスと組み合わせる**(例: 「ポータル状の
      パーティクル演出」という要素だけを取り、色や構図は別のリファレンスから合わせる)。抽出した演出要素は
      Option B(下記Phase4)のパターンの1つとして実装するとよい — パーティクルの分布形状・色・光源・動きの
      数式を変えるだけで、同系統の演出は再現コストゼロで作れる

次フェーズへ進める条件: レイアウト/グラフィックス/カラーの3カテゴリそれぞれに最低数枚ずつ集まっていること。

## Phase 2: AIスタイル統合とアセットの構造的分離
ツール: Hickfield等の画像生成AI

- [ ] 属性指定を厳格化したプロンプトを書く:「画像1のレイアウトを維持し、画像2のテクスチャを適用せよ」
- [ ] 不要要素はネガティブプロンプトではなく **具体的な削除指示** で排除する:「不要な黄色の円を削除せよ」「ナビゲーションバーを除去せよ」
- [ ] 背景アセット(Background Only)を生成: 4K/8K、テキスト・ボタン・アイコン・ロゴを完全排除した純粋な背景
- [ ] UI構造イメージを生成: Pure Black背景の上にテキストとアイコンの配置位置のみを示す

なぜ分離するか: 背景=画像として固定・UI=DOM(コード)として管理することで、レスポンシブ崩れとテキストの
「焼き込み」歪みを防ぐ。SEOフレンドリーな構造も両立できる。

次フェーズへ進める条件: 背景アセットとUI構造イメージが**別ファイルとして**揃っていること(1枚に混在させない)。

## Phase 3: Claudeによるフロントエンド実装とタイポグラフィ
プレビュー環境: **Fable 5 を強制使用**

- [ ] スクリーンショットを「Top Popular Google Fonts」リストと照合し、フォントを人間が同定する
      (AIのフォント推測は精度が低いので必ず人間が確認する)
- [ ] 具体的なフォント名を実装プロンプトに明記する。例:「Instrumental Serifを特定した。Google Fontsからインポートせよ」
- [ ] 実装プロンプトに以下を必ず含める:
  - `Pure Black Background (#000000)` の環境指定
  - `Make sure everything is mobile responsive` のフレーズ
  - アイコンライブラリのimportとホバーエフェクト等の動的要素の指示

次フェーズへ進める条件: レスポンシブ崩れがないこと、フォントが具体名で固定されていること。

## Phase 4: ダイナミック・バックグラウンド (任意)
静的サイトで十分な場合はスキップ可。2つの実現方法がある — 迷ったらOption A(実装コストが低い)から。

- **Option A: 動画生成AI(Luma / Kling)でループ動画を敷く** — 非インタラクティブだが実装が軽い
- **Option B: Three.js/WebGLでライブな3Dシーンをコードとして実装する** — カーソル反応やパーティクル等
  インタラクティブ性が要る場合のみ選ぶ。動画では出せない演出が可能な一方、実装・デバッグコストは上がる

### Option A: 動画生成AIでループ動画を敷く

- [ ] CleanShot等で参考サイトの **モーション部分だけ** を数秒間録画する
- [ ] 録画をリファレンスとしてアップロードし、「色や要素は無視し、動き(Effect)の質感のみを抽出して静止画に適用せよ」と指示する
- [ ] 10秒程度・`No zoom / No zoom out` 設定でシームレスループを生成する
- [ ] **ループは後処理で誤魔化す前に、生成時点で作り込む**:
  - image-to-video で始点/終点フレームを指定できるモデル(例: Kling の `tail_image_url`)では、
    **終点フレームに始点と同じ画像を指定する**(`tail_image_url = image_url`)。始まりと終わりが同じ絵になるので、
    ネイティブにシームレスなループが得られ、後段のクロスフェード処理が不要になる
  - 始点/終点フレーム指定に対応しないモデルでは、プロンプトに「一方向の動き」(ドリフト・展開・変形など、
    終端が始端と別の状態になる動き)ではなく **周期運動**(呼吸・ゆるやかな回転で元の向きに戻る・脈動など、
    終端が始端に近い状態へ戻る動き)を明示的に指示する
  - どちらも使えない場合のみ、実装側のフォールバックとして2本の`<video>`をクロスフェードする(下記)
- [ ] 動画背景導入時の可読性調整を行う:
  - ヘッドラインのフォントサイズを **30%程度縮小**
  - 既存のディバイダー線を削除(動画自体が区切りになるため)
- [ ] 実装時は `<video>` を単に敷くだけにしない: 暗幕グラデーション(`::before`)は動画より **後**(paint順で上)に来るよう
      `z-index` を明示する(`::before` に `z-index` が無いと `::before` は生成上「最初の子」扱いになり、通常のDOM順で
      後に置いた `<video>` の**下**に潜って暗幕が効かなくなり、テキストが埋もれる)
- [ ] (フォールバック) 始点/終点フレーム指定も周期運動プロンプトも使えず継ぎ目が揃わない場合は、`loop` 属性任せにせず、
      同じ動画を2本(`<video>`を2つ)重ねて、終端 **1〜2秒手前**でJSにより次の動画の再生開始+`opacity`クロスフェードを行い、
      継ぎ目を隠す(片方の`<video>`だけでは必ず一瞬のジャンプカットが出る)

### Option B: Three.js/WebGLでライブな3Dシーンを実装する
背景/UI分離のためのアセット生成(Phase 2)は不要 — 背景そのものをコードで描画する。

- [ ] Claudeに実装させる内容を具体的に指示する: 例)カーソル追従の3Dオブジェクト、ネオン風ライティング、
      スクロール連動のパーティクルメッシュ、モーションブラー
- [ ] **Phase1の「3方向提案」はOption Bと相性がいい**: renderer/camera/疑似モーションブラーの土台を1つ共有し、
      シーン構築関数(オブジェクト・色・光源・動きの数式)だけを差し替えれば、**再生成コストゼロで複数パターンを
      即座に切り替え比較**できる(Option Aの動画ループは1案ごとに生成コストと待ち時間が発生するため不利)。
      クライアントに複数方向を見せたい場合は、動画を作り分けるより先にOption Bでのパターン出しを検討する
- [ ] **Phase1で集めた「核となるオブジェクト」を3Dで出すなら skill `img2threejs` を使う**(2026-08-14 導入・スモークテスト済)。
      参照画像1枚 → 手続き的な `createXxxModel.ts`(`THREE.Group` を返す factory)を生成する。
      呼び出しは `/img2threejs <画像> Rebuild this object as a Three.js model, keep proportions, angles, colours.`
  - **接続点はパターン登録関数の中だけ**: 生成された factory を import して `scene.add(createXxxModel())` するだけで、
    下記のPostFXプラグイン(残像/ブルーム/FilmPass)もパターン切り替え機構もそのまま乗る。配線コードは要らない
  - **使ってよいのは「主役オブジェクト1個」に限る**。8パス×決定論ゲート×vision review を回すのでトークンと時間を食う。
    背景のパーティクル・グラデーション・光の帯のような**形が曖昧なもの**は従来どおり直接書いたほうが速い
  - 得意なのは**ハードサーフェス**(工業製品・機械・器物)。有機物やキャラクターは本人が「様式化された再構成」と明言しており、
    Phase1で「蝶」「枝」のような有機物を核に選んだ場合は期待値を下げるか、Option Aの動画側に回す
  - **仕様が浅いとTS生成そのものが拒否される (fail-closed)**。`generate_threejs_factory.py` は strict-quality を通らないと
    `status: BLOCKED` を返して1行もコードを出さない。これは不具合ではなく仕様 — 出力が無いときは `cause` 配列に
    「何が足りないか」が列挙されているので、コードではなく **spec を直す**(`refine-spec`)
  - 実行は `python3`(README準拠)。本プロジェクトの `py` 規約はリポジトリ内コードの話で、この skill は
    `~/.claude/skills/img2threejs` にある外部リポジトリなので適用外
- [ ] **モーションブラーはEffectComposer等の追加ライブラリなしで疑似実装できる**: `renderer.autoClear = false`
      にした上で、毎フレーム (a) `renderer.clearDepth()` でdepthだけクリア → (b) 低不透明度(例: `opacity: 0.16`)の
      黒い全画面Plane(`OrthographicCamera`)を先に描画 → (c) 本シーンを重ねて描画、の順にすると前フレームが
      薄く透けて残像(トレイル)になる。ネオン管のような発光表現と相性が良い。**まずはこちら(依存追加ゼロ)から**
- [ ] **ブルーム(強い発光)等それ以上の効果が要る場合は、PostFXをプラグイン化して追加する**。実装・実測済みの構成:
  - シーン構築(パターン=何を描くか)と後処理(プラグイン=どう仕上げるか)を分離する。パターン側は
    `{ scene, update(dt,t) }` を返す関数として登録し、プラグイン側は `{ トリガー名: (composer,w,h,ctx) => Pass }`
    という**レジストリオブジェクト**に登録する。有効なプラグインの集合が変わるたび
    (パターン切り替え時・チェックボックス変更時)に `composer` を作り直せば、パターン×プラグインの
    全組み合わせが事故なく動く(実測済み: 3パターン×残像/ブルームの全組み合わせ、144fps安定)
  - `three/examples/jsm/postprocessing/` の `EffectComposer`/`RenderPass`/`UnrealBloomPass`/`AfterimagePass` を使う
    (疑似モーションブラーは`AfterimagePass`に置き換えられる — dampパラメータは「1 - 疑似実装のopacity」相当)
  - **r150以降のjsmアドオンは`"three"`をbare specifierでimportするため、`<script type="importmap">`で
    `"three"`と`"three/addons/"`をCDN URLにマッピングし、`<script type="module">`から読み込む必要がある**
    (Option Aや前述の疑似モーションブラー版で使っていたUMDグローバル版`three.min.js`とは読み込み方が別物)
  - **`composer`の最後には必ず`OutputPass`を足す**(発色・色空間の補正パス。省略すると`EffectComposer`経由の
    出力だけ色味がずれる)。これは選べる「効果」ではなく必須の締めパスなのでレジストリには入れず固定で追加する
  - このプラグイン化はコストが上がる(ESモジュール化・追加HTTPリクエスト)ので、疑似実装で足りるうちは
    そちらを使う。「ネオン管程度の発光」は疑似実装で十分、「強いブルームで白飛びさせたい」場合のみ導入する
- [ ] **他に候補になるプラグイン**(優先度が高い順。実装・実測済みは◎、API仕様は既知だが今回は未実測は○):
  - ◎ `FilmPass`(グレイン/質感) — マニュアル本文が繰り返し警告する「AI生成物特有の平坦さ」を打ち消す効果が
    直接効く。`new FilmPass(intensity)` の1引数で十分(旧APIの4引数版とは別物なので古い解説記事に注意)
  - ○ `OutlinePass` — 特定オブジェクトだけを選択的に縁取り発光させる。カーソルを乗せた3Dカードを光らせる、
    といった「ホバー時だけ反応する」UIに向く(Phase3のカード型UIと組み合わせる想定)
  - ○ `SMAAPass` / `FXAAPass` — アンチエイリアス。`EffectComposer`を経由すると解像度ダウンサンプル等で
    輪郭のジャギーが再度出やすくなるため、パス構成の最後(`OutputPass`の直前)に足すのが定石
  - 効果が強すぎて「AI生成物っぽさ」を逆に強調するので**基本的に避ける**: `GlitchPass`(グリッチ演出は
    ネタ的で商用ポートフォリオの質感とは相性が悪い)、過度な`BokehPass`(被写界深度。狙いすぎた映画っぽさが
    かえって安っぽく見えるリスクがある。使うなら控えめに)
- [ ] **必ず用意するフォールバック**: `prefers-reduced-motion`時は静止画/CSSアニメーションへ切り替える、
      WebGL非対応ブラウザでは`<canvas>`の代わりにPhase2相当の静的背景を出す。実装パターン:
  - reduced-motion判定は `matchMedia('(prefers-reduced-motion: reduce)').matches` を**レンダラー初期化より前**で
    早期returnする(CSSで`<canvas>`を隠すだけだとJSのアニメーションループはCPU/バッテリーを消費し続けたまま無駄に走る)
  - WebGL非対応は `new THREE.WebGLRenderer(...)` を `try/catch` で包み、失敗したら親要素に`no-webgl`クラスを
    付与してCSS側で`<canvas>`を隠し代わりの静的背景`div`を出す(featureテストより実際に生成を試みて失敗を拾う方が確実)
- [ ] **必ず検証する**: モバイル/低スペック機でのFPS低下、複数`<canvas>`間のWebGL context競合
      (同時に張れるcontext数には上限がある)、初回ロード時間(重いシーンはLCPを悪化させる)
- [ ] 実装後は実機(できればモバイル実機)でFPSを確認してから次フェーズへ進む。**「実装した」≠「検証した」**:
      reduced-motion/WebGL非対応のフォールバックはコードを書いただけでは検証済みとは言えない。ブラウザの
      デバイスエミュレーション等で実際にトリガーして動作を目で確認するまではTODOとして残す
  - **OS設定のエミュレーションが使えない環境での代替検証法**: 実装に `?reduce=1` / `?nowebgl=1` 等の
    URLクエリパラメータで各フォールバック分岐を**強制的に**踏める入口を仕込んでおく(例: `matchMedia`の判定に
    `|| new URLSearchParams(location.search).has('reduce')` を足す、WebGL初期化を`try`する前に`nowebgl`が
    あれば意図的にthrowする)。ブラウザのOSレベル設定を変更する権限/手段が無いツール環境でも、
    「canvasが実際に0個生成されない」「three.jsへのfetch自体が0件になる」ところまで実測で確認できる
    (2026-08-08: Opus 5にSKILL.mdだけを渡して独立実装させた際にこの検証法が使われ、有効性を確認した)

## Phase 5: 商用クオリティへのブラッシュアップ(魂の吹き込み)
このフェーズを飛ばすと「AI生成物」だと一目でバレる。省略不可。

- [ ] AIアーティファクト(不要なストローク/外枠・不要な塗り)をコード上で **手動監査して削除**
- [ ] 有機的セクション・ディバイダー: 背景透過させたAI生成オブジェクトを `position: absolute` でセクション境界に重ねる
- [ ] セクション間パディングを **200〜300px** 確保し、視覚的な呼吸スペースを作る
- [ ] モバイルスタッキングを個別に指示する: デスクトップで横並びの要素(例: 3要素)は、モバイルでも
      **あえて1行に小さく並べる** よう指定し、縦長になりすぎるのを防ぐ

## 進行管理のルール
- 各フェーズの「次フェーズへ進める条件」を満たすまで次に進まない
- Phase 5 を時間短縮のために省略しない(ここがAI生成物と職人仕事の分かれ目)
- 案件ごとに Phase 1 の収集結果(Figmaボード)を残す — 次回の別案件との使い回し(デッドコピー化)を防ぐため
