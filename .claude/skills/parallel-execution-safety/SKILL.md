# Parallel Tool Execution Safety

- **並列化の効果は「最も遅い1本」に律速される。速い方を何本足しても縮まらない**。fan-out は同種3件 (`tool_web_search` ×3) では 12.3秒 → 4.2秒 (2.9x) だったが、`web_search` (4.5秒) + `vault_hybrid_search` (16.3秒) の2件では 20.8秒 → 16.3秒 (1.3x) にしかならない — 速い方が遅い方の中に完全に隠れるだけ。**遅い1本を速くする方が効く局面がある**ことを、並列化に手を出す前に見積もる。なお `saved_seconds` は各ステップの所要時間に**共有資源の待ち時間** (`lib.concurrency.ollama_slot`) が混ざるので、資源を奪い合うステップを並べると過大に出る → 最低保証値として読まない
- **並列化の依存判定を LLM に書かせない。既に持っている契約を読む**。Planner に `depends_on` を宣言させると、依存を1本落とした競合状態が黙って混入する (落とし方が安全側にならない)。`generate_plan` のプロンプトは既に「前ステップの結果に依存する引数は `args_json` を空にして `args_hint` だけ書く」と指示しているので、**`args_json` が使える＝データ依存が無い**と読めば新しい判定は要らない。これに「レジストリで `parallel_safe` が宣言されている」を AND して副作用の順序依存も潰す。**並列可否は必ず opt-in** — 付け忘れは逐次のまま (安全) だが誤って付けるとデータ競合が黙って起きる、という非対称性があるため。`tests/test_tool_registry.py` が集合をピン留めし、**どちらのリストにも載っていないツールがあると落ちる** (「判断されていない」状態を作らせない)
- **「取得系だから並列にしてよい」を呼び出し口の名前で決めない**。`tool_get_calendar` は取得系だが、主経路 (gws CLI) が失敗したときのフォールバック `_get_calendar_service()` が (a) `token.json` を書き換え、(b) 期限切れ時に `InstalledAppFlow.run_local_server()` でブラウザ認証を待つ。ワーカースレッドでこれが起きるとウェーブ全体が無言で止まる。**実装を最後まで読んでから分類する**
- **並列性を壁時計のしきい値で判定しない。区間を記録して「重なった本数」で見る**。同じ形が **3件** 連続で CI を赤くした: `tests/test_sweep_runner.py` の `wall < 7.0` (CI 実測 7.0 で境界・**同じコミットが緑と赤を往復**)、`tests/test_parallel_execute.py` の `wall < 1.0` (CI 実測 1.42秒)。開発機 (16コア・非競合) では3〜9倍の余裕があるので永久に緑になる。とくに **スイープ自体が8並列になってから**、「自分の高速化を計測するテスト」が他7本と CPU を取り合うようになり、**並列化したことで並列性のテストが壊れた**。→ ツールのスタブ / プローブに `(start, end)` を記録させ、イベントの sweep line で **peak concurrency** を出す。逐次なら必ず 1 になるので方向が確定する
- **もっと危険なのは逆向き。「逐次である」を壁時計の下限で主張すると、何も証明しなくなる**。`check("逐次相当の時間がかかる", wall >= 0.55)` は、混雑した runner では**並列実行でも**軽く超える (実測: 0.5秒×3本の並列が 1.42秒) ため、fan-out が誤って有効なままでも緑になる。赤くなる flaky より、**緑のまま無意味になる方が見つからない**。`peak == 1` なら誤りようがない
- **peak を使うときは (a) しきい値を `>= 2` にする (b) 観測ウィンドウを遅延より長くする**。`peak == N` は「N本同時に走れたか」= **OS のスケジューリングの速さ**を測ってしまい、壁時計をやめても machine gauge のままになる (2026-07-31 に実際に2回目の修正が必要になった)。fan-out の幅は `min(len(wave), fanout_workers())` で CPU 数から導出していないので、**submit されたか (`waves == 1` + `len(results)`) と、逐次でないか (`peak >= 2`) に主張を分ける**。また sleep がスレッド起動の遅れ (実測 約0.7秒) より短いと、3本 submit しても重なりが観測されない → 2倍の余裕を取る (0.5 → 1.5秒)
- **並列プローブが「区間を記録する」ためのログ自体が、Windows では複数プロセス同時追記で行方不明になることがある** (2026-08-03)。上の3件で導入した `(start, end)` 記録方式が、CI で1回だけ `tests/test_sweep_runner.py` [2]「6本すべての区間が記録された」を落とした。原因は `_PROBE` テンプレートが全プローブから**同一の jsonl ファイル**へ `open(path, "a", encoding="utf-8").write(...)` で追記していたこと — Windows の CRT は `O_APPEND` を「毎回 EOF へ seek してから write」でエミュレートしており、POSIX と違ってプロセス間で原子的でない。並列レーンで4本前後が数十ms差で追記すると後勝ちで既存の1行がそっくり消える (8プロセス同時追記を30試行し、1試行で1行消失を実機再現)。しきい値を緩める・リトライを足す対症療法は取らず、**共有ファイルへの追記をやめ1プローブ=1ファイルにする**構造修正にした — `SWEEP_PROBE_LOG` を「ディレクトリ」として扱い、各プローブが `<dir>/<name>.interval.json` に `"w"` で自分専用ファイルを書き (追記ではない・1ライター1ファイル)、読み取り側は `os.listdir` で列挙する。**「複数プロセスが同じファイルへ書く」設計を Windows で見たら、`open(path, "a")` だけでは原子性が足りないと疑う** — 上の3件が「計測方法 (壁時計 vs peak concurrency)」の罠だったのに対し、これは「計測用のログ自体の書き込み方式」の罠で原因の層が一段違う
