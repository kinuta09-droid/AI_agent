# 価格予想を補強する理論・システムの検討

> 対象: `lib/quant_core.py` / `tools/tool_crypto.py` / `tools/tool_crypto_watcher.py` /
> `scripts/backtest_crypto.py`
> 位置づけ: **検討メモ**。実装計画ではない。ここから1件を選んで Plan Mode に入る想定。
> 作成: 2026-07-30

---

## 0. 結論を先に

推奨順は以下。**上2つ以外は、下地 (Tier 4) を先に入れないと「測れたつもり」になる。**

| # | やること | 何が直るか | 既存構造への影響 |
|---|---|---|---|
| 1 | **取引コストとウォークフォワードをバックテスト器に入れる** | 現状の期待値 -0.01R が「ほぼゼロ」なのか「実はマイナス」なのか確定する | バックテスト器のみ |
| 2 | **メタラベリング** (既存ルールは残し、勝率予測だけをモデル化) | `confidence` が定数である問題と、Kelly の入力が架空の数字である問題を同時に | 加算のみ。ルール層は不変 |
| 3 | **ボラティリティ正規化** (固定%閾値 → σ倍数) | 銘柄・局面をまたいで閾値の意味が一定になる | `_detect_regime` / watcher 閾値 |
| 4 | **ファンディングレート + 建玉** を特徴量に追加 | 唯一「価格以外」を見る情報源。逆張り戦略と相性が最も良い | 特徴量追加 (履歴取得可 = 検証可能) |
| 5 | **クロスセクション (相関) の把握** | 20銘柄が実質1つの β ベットである問題 | ポートフォリオ層 (現状ゼロ) |

「新しい指標を足す」より先に、**今ある数字が信用できるかを確定させる**のが最優先という判断。
理由は §1 の最後に書いた。

## 1. 現状の診断 — 「予想」はどこで作られているか

予想を作る過程を5層に分解すると、補強の余地がどこにあるかが見える。

```
[L1 情報源]   Binance 4h OHLCV (単一取引所・現物のみ) + F&G指数 + Tavilyニュース
                                   ↓
[L2 特徴量]   RSI/EMA50/EMA200/ADX/ATR/DMI + 流動性スイープ + RSIダイバージェンス
              (quant_core._compute_indicators)
                                   ↓
[L3 判定]     if/elif カスケード 4分岐 (smc_sweep / panic_reversal /
              trend_pullback / rsi_oversold)   (quant_core._decide_signal)
                                   ↓
[L4 確率]     confidence = 0.65 / 0.55 / 0.35  ← ★定数。判定分岐ごとの固定値
              n>=20 で実測勝率に切替 (tool_crypto._resolve_win_rate)
                                   ↓
[L5 サイズ]   フラクショナル・ケリー (reward_ratio=2.0, fraction=0.25)
              (quant_core._calculate_kelly)
                                   ↓
[出口]        SL = 2.5×ATR / TP = 2R固定 / 21日で期限切れ
```

### 決定的な数字

- **損益分岐勝率は 33.3%**。WIN=+2R / LOSE=-1R なので `2p - (1-p) = 0 → p = 1/3`。
- **既定 confidence 0.65 は、資金の 11.9% を張る指示になる**。
  `_calculate_kelly(0.65)` = `(0.65×2 - 0.35)/2 × 0.25 × 100` = 11.9%。
  0.55 → 8.1%、0.35 → 0.6%。
- **バックテスト実測の期待値は -0.01R** (`tool_crypto.py:352-353` の記述、730日×3銘柄)。

この3つを並べると、現状の構造がはっきりする:

> 実測期待値がほぼゼロ (= 真の勝率が 33% 近辺) の戦略に対して、
> L4 が「勝率 65%」と申告し、L5 がそれを信じて資金の 11.9% を張っている。

つまり **今のシステムで最も脆いのは「予想の精度」ではなく「予想の確信度が根拠を持っていないこと」**。
新しい指標を足して勝率を 33% → 36% にする作業より、L4 を実測に接続する作業のほうが
リスク調整後リターンへの寄与が大きい。これが §0 の順位の根拠。

## 2. 弱点の特定

### W1. `confidence` が確率ではない — L4

`_decide_signal` が返す 0.65 / 0.55 / 0.35 は、分岐ごとに人が決めた定数。
これがそのまま Kelly の `win_rate` に入る。校正 (calibration) されていないので、
「confidence 0.65 の予測群の実際の勝率は?」という問いに答える仕組みがない。

さらに `_resolve_win_rate` の切替が **崖** になっている:

| 判定済み件数 | 使う勝率 | Kelly% |
|---|---|---|
| n=19 | 0.65 (既定値) | 11.9% |
| n=20, 7勝13敗 | 0.35 (実測) | 0.6% |

1件決着しただけでポジションサイズが **20倍変わる**。統計的な意味はない。

**加えて、EXPIRED が勝率計算から除外されている** (`_get_signal_stats` は WIN/LOSE のみ集計)。
Kelly は「賭けが必ず勝ち負けで決着する」前提の式なので、21日間資金を拘束して 0R で
終わる玉が母集団から消えていると、**単位時間あたりの優位性を系統的に過大評価する**。

### W2. 情報源が価格と出来高しかない — L1

L1 に入っているのは実質「Binance 現物の4h足」だけ。F&G は市場全体で1日1値なので
銘柄の識別力はなく、ニュースはキーワード分類 (しかも `SYSTEMIC_RISK` は遮断にしか使われず、
予想を上向きに補強することはない)。

暗号資産に特有で、かつ **無料または低コストで履歴まで取れる** 情報源が丸ごと未使用:

- 永久先物のファンディングレート / 現物-先物ベーシス
- 建玉 (Open Interest) の変化
- 清算 (liquidation) の集積
- 銘柄間の相対力・BTC ドミナンス

### W3. 閾値がすべて固定値の崖 — L2/L3

`RSI < 30`、`ADX > 25`、`ATR% > 3.0`、watcher の `±2.5% / 15分`。
すべて「その値をまたいだ瞬間に判定が反転する」ステップ関数で、しかも
**20銘柄すべてに同じ数値を当てている**。

BTC の 2.5%/15分 と DOGE の 2.5%/15分 は統計的にまったく別の事象だが、
watcher は同じ閾値で発火する。結果、高ボラ銘柄では鳴りっぱなし、低ボラ局面では
何も起きない。ATR%>3 の VOLATILE 判定も同じ性質。

### W4. 20銘柄が独立に扱われている — ポートフォリオ層が存在しない

`_evaluate_symbol` は1銘柄ずつ完全に独立に評価する。
`_has_open_record` は「同一銘柄・同一種別の OPEN は1件」を担保するが、
**ポートフォリオ全体の建玉数・合計リスクに上限がない**。

主要アルト20銘柄は対 BTC で高相関なので、市場全体が売られた局面では
`panic_reversal` (F&G<20 + RSI<25) が **全銘柄で同時に成立する**。
そのとき Kelly の指示は「各 11.9%」であり、合計は資金を超える。

現状これを偶然抑えているのは `SWEEP_COUNTER` (Gemini の日次予算) だけで、
これは **コスト管理であってリスク管理ではない**。予算を上げた瞬間に露出する。

### W5. 検証にコスト・多重検定・OOS がない — 評価層

`scripts/backtest_crypto.py` を読むと、以下がすべて無い (grep で確認済み):

- 手数料・スリッページ・ファンディング支払い
- 学習/検証の分割 (ウォークフォワード)。全期間を1つのパラメータ設定で通している
- 多重検定の補正。`--compare` で設定を変えて比べる設計なので、**試行回数が増えるほど
  「良く見える設定」が偶然見つかる確率が上がる**
- ベンチマーク (バイ&ホールド、ランダムエントリー) との対比

そして `EXPIRED = 0R` という扱いは、**21日後に手数料ゼロ・スリッページゼロで
建値決済できた** という仮定に等しい。現実には市場価格での手仕舞いになる。

> このリポジトリが繰り返し踏んできた「表示と実態の食い違い」の、定量版がこれ。
> 見出しが ✅ なのに learning_db が failed だった問題と、
> バックテストが +0.4R なのに実運用が -0.1R になる問題は、**同じ形をしている**。
> 前者には `is_failure_result()` という単一の判定関数を作って決着させた。
> 後者にはまだ対応する「1箇所」が無い。

## 3. 候補となる理論・システム

各項目に **[何を直すか] / [実装コスト] / [検証可能性] / [リスク]** を付す。
検証可能性が「不可」のものは、どれだけ理屈が良くても Backtest Gate を通せない。

---

### Tier 1 — 既存構造を壊さず、今のバックテスト器で測れるもの

#### 1-1. メタラベリング (Meta-Labeling) ★本命

López de Prado『Advances in Financial Machine Learning』第3章。
**一次モデル (いつ買うかを決める) と二次モデル (その判断が当たるかを予測する) を分離する**手法。

```
既存の _decide_signal      →  「BUY を検討する局面か」 (side)     ← そのまま残す
新設のメタモデル            →  「この BUY は勝つか」 P(win)        ← Kelly の入力に
```

このリポジトリに異常なほど噛み合う理由が3つある:

1. **ラベリング器がすでにある**。メタラベリングの標準的な正解ラベルは
   「トリプルバリア法」(上バリア=TP / 下バリア=SL / 縦バリア=時間切れ) だが、
   `quant_core._resolve_trade` が **まさにそれ** (TP / SL / 21日 expiry)。
   ラベル生成のコードを書く必要がない。
2. **学習データを取る仕組みもすでにある**。`scripts/backtest_crypto.py` を1回走らせれば
   (特徴量, WIN/LOSE/EXPIRED) の組が全期間分出る。
3. **`record_kind=observation` が眠っている教師データそのもの**。
   WATCH LIST を「仮にエントリーしていたら」で追跡している対照群は、現状
   `_get_signal_stats` から除外されるだけで **どこからも使われていない**。
   これは「見送った限界的なトレードが実際どうなったか」のラベルで、
   メタモデルにとっては最も情報量の多いサンプル。

出力の使い方も既存構造に収まる:

- P(win) が閾値未満 → `BUY` を `WATCH LIST` に降格 (= `_apply_daily_gate` と同じ形)
- P(win) をそのまま `_resolve_win_rate` の戻り値として Kelly へ

| | |
|---|---|
| 何を直すか | W1 (確信度の根拠) / W2 の一部 (特徴量を増やしても判定ロジックを書き換えなくて済む) |
| 実装コスト | 中。特徴量抽出は `_compute_indicators` の戻り値がほぼそのまま使える |
| 検証可能性 | **高**。ただしウォークフォワード必須 (§Tier 4) — 全期間で学習して全期間で評価したら無意味 |
| リスク | 過学習。730日×3銘柄では **トレード数が数十件規模** になるはずで、この標本数で
勾配ブースティングを回すのは危険。まずはロジスティック回帰など低分散のモデルから |

**このリポジトリ固有の設計上の注意**: `lib/quant_core.py` は
「pandas / pandas_ta のみに依存する純関数層」という制約を持つ。
学習済みモデルの推論をここに置くなら、依存を増やさない形 (係数を定数として埋め込む、
または `lib/` に別モジュールを立てて `quant_core` は係数だけ受け取る) にしないと、
オフラインのバックテスターから使えなくなるという既存の設計意図を壊す。

#### 1-2. 確率キャリブレーションと Brier スコア

メタラベリングを入れなくても単独で意味がある、最小の一歩。

「confidence 0.65 と申告した予測群の、実際の勝率は何%だったか」を測る
**信頼度図 (reliability diagram)** と **Brier スコア** を監査レポートに出す。
そのうえで Platt スケーリング (ロジスティック回帰) か等調回帰 (isotonic regression) で
申告値を実測に写像する。

| | |
|---|---|
| 何を直すか | W1 |
| 実装コスト | **小**。`tool_crypto_stats.py` の集計に列を足すのと、写像関数1つ |
| 検証可能性 | 高 |
| リスク | 低。等調回帰は標本が少ないと階段状に過学習するので、標本 <100 では Platt を使う |

#### 1-3. Beta-Binomial による勝率の縮小推定

W1 の「n=20 の崖」を消す。実測勝率を生で使う代わりに、
既定 confidence を事前分布の中心に据えた Beta 事後分布の平均を使う:

```
p_hat = (wins + α) / (wins + losses + α + β)      α, β は既定confidenceを中心に設定
```

n=0 では既定値、n が増えるにつれ滑らかに実測へ寄る。
`MIN_AUDIT_SAMPLES = 20` と `EMPIRICAL_WIN_RATE_CAP = 0.75` という
2つのアドホックな定数を、1つの事前分布に置き換えられる。

さらに **Kelly をベイズ化する** 拡張もある: 事後平均をそのまま使うのではなく、
事後分布の不確実性ぶんサイズを引く。現状の `fraction=0.25` という固定の掛け目は
まさにこの不確実性への保険を手で入れたものなので、理論的に置き換わる。

| | |
|---|---|
| 何を直すか | W1 (崖) |
| 実装コスト | **小**。`_resolve_win_rate` の中だけ |
| 検証可能性 | 高 (バックテストで玉ごとのサイズ推移を比較できる) |
| リスク | 低 |

**併せて直すべき**: EXPIRED を勝率母集団から外している件 (W1 後段)。
「勝ち / 負け / 期限切れ」の3値を素直に扱うなら、Kelly ではなく
期待 R と分散から直接サイズを出す形 (期待値ベースの最適比率) に寄せる選択肢もある。

#### 1-4. ボラティリティ正規化 (固定% → σ倍数)

W3 への直接の対処。「2.5%動いた」ではなく「直近の実現ボラの 2.5σ 動いた」で判定する。

適用箇所は3つ:

- **watcher の急変閾値** (`WATCH_DELTA_15M` / `WATCH_DELTA_1H`) —
  銘柄ごとに閾値が自動調整され、BTC と DOGE を同じ基準で扱う不整合が消える
- **レジーム判定の `ATR% > 3.0`** — 絶対値ではなく、その銘柄自身の ATR% の
  過去分位点 (例: 80パーセンタイル超) にする
- **ポジションサイズ** — ボラティリティターゲティング。
  Kelly% にさらに `目標ボラ / 実現ボラ` を掛け、リスク量を局面によらず一定に保つ
  (現状の `regime == "VOLATILE" なら ×0.5` を連続量にしたもの)

| | |
|---|---|
| 何を直すか | W3、W1 の一部 |
| 実装コスト | 小〜中。watcher 側は純関数 `_decide_watch_actions` の引数追加で済む |
| 検証可能性 | 中。watcher の発火頻度はバックテスト器の対象外 (バックテストは4h足クローズ毎の評価) なので、**発火ログの前後比較**という別の検証手段が要る |
| リスク | 低。ただし watcher は「無料の検知層」なので、σ 化で発火が増えると有料層 (Gemini) の呼び出しが増える。`WATCHER_COUNTER` の上限との相互作用を先に確認する |

### Tier 2 — 新しい情報源 (無料〜低コスト、履歴が取れる = 検証可能)

W2 への対処。**「履歴が取れるか」が Backtest Gate を通せるかの分かれ目**なので、そこで仕分ける。

#### 2-1. ファンディングレート / 永久先物ベーシス ★推奨

永久先物のファンディングレートは「ロングとショートのどちらが対価を払っているか」、
つまり **レバレッジを掛けた市場参加者のポジションの偏り** を直接示す。

現行戦略は逆張り主体 (`panic_reversal` / `rsi_oversold` / `smc_sweep`) なので、
噛み合いが良い:

- ファンディングが強くマイナス + RSI 売られすぎ = ショートが混み合った投げ売り
  → 現行の `panic_reversal` を **補強する** 情報
- ファンディングが強くプラス + RSI 売られすぎ = ロングがまだ耐えている
  → 同じ RSI でも意味が違う。**現行ロジックはこの2つを区別できない**

取得は `ccxt` でできるが注意点がある: 現行コードは `ccxt.binance()` = **現物**。
ファンディングは USDT 建て永久先物なので `ccxt.binanceusdm()` を別に立てる必要がある。
履歴は `fetch_funding_rate_history` で遡れる = **バックテスト可能**。

> ⚠️ **未検証**: この文書を書いた環境に ccxt が入っておらず、
> `binanceusdm` の `has['fetchFundingRateHistory']` と実際に遡れる期間を確認できていない。
> 実装に入る前に開発機で `py -c "import ccxt; print(ccxt.binanceusdm().has)"` で確認すること。

| | |
|---|---|
| 何を直すか | W2 |
| 実装コスト | 中。`lib/bt_data.py` にキャッシュ層を1つ足す (OHLCV と同じ作りでよい) |
| 検証可能性 | **高**。履歴が取れる |
| リスク | 8時間ごとの離散値なので、4h足に合わせるとき **先読みしない** ように結合する必要がある (F&G を「バー開始日の公表値」で引いている `backtest_crypto.py:100` と同じ配慮) |

#### 2-2. 建玉 (Open Interest) の変化

価格と OI の組み合わせで、値動きの性質が分類できる (古典的な先物の読み方):

| 価格 | OI | 解釈 |
|---|---|---|
| 下落 | 減少 | 手仕舞い・清算の投げ。**下落の終盤に多い** |
| 下落 | 増加 | 新規ショートの参入。**下落継続を示唆** |
| 上昇 | 増加 | 新規ロード。トレンド継続 |
| 上昇 | 減少 | ショートカバー。上昇が続きにくい |

現行の `is_falling_knife` (ADX>30 かつ DM->DM+) は価格だけで「まだ落ちる」を判定しているが、
OI を足すと **「投げが出切ったナイフ」と「まだ刺さるナイフ」を分けられる**。
これは現行の最も重要な遮断ロジックの精度に直結する。

| | |
|---|---|
| 何を直すか | W2、特に `is_falling_knife` の識別力 |
| 実装コスト | 中 |
| 検証可能性 | 中〜高。`fetch_open_interest_history` は取れるが、**取引所によって遡れる期間が短い** (Binance は概ね30日程度)。730日のバックテストには足りない可能性が高い → 有料データソースか、前向き検証に切り替えるかの判断が要る |
| リスク | 上記の履歴長。**先に取得可能期間を確認してから設計する** |

#### 2-3. クロスセクション: 相対力と相関 ★W4 の解

W4 (20銘柄が実質1つの β ベット) への対処であり、同時に予測の補強でもある。

- **対 BTC 相対力**: 各アルトを USDT 建てだけでなく **BTC 建て** でも見る。
  「BTC も一緒に下げている」のか「この銘柄だけが売られている」のかで、
  逆張りの意味が変わる。現行はこれを一切区別していない
- **BTC ドミナンス / 資金ローテーション**: 市場全体の局面
- **相関クラスタリング**: 20銘柄の日次リターン相関からクラスタを作り、
  **同一クラスタからの同時建玉に上限を設ける**。
  これがポートフォリオ層の最小実装になる

| | |
|---|---|
| 何を直すか | W4、W2 |
| 実装コスト | 中。データは既に取っている (SCAN_SYMBOLS の OHLCV) ので **新規の外部依存ゼロ** |
| 検証可能性 | **高**。ただし現行バックテスト器は「銘柄ごとに独立ループ」の構造なので、
ポートフォリオ制約を入れるには `run_backtest` を **時系列横断のループに書き換える必要がある** (`run_symbol` を銘柄ごとに回して結合する今の形では、同時建玉数を数えられない)。これは小さくない改修 |
| リスク | 上記の構造改修。ここが本検討でいちばん工数が読みにくい |

#### 2-4. 板情報の非対称性・清算ヒートマップ

板の厚みの偏り、清算価格の集積帯。理屈としては流動性スイープ (`_detect_liquidity_sweep`) の
上位互換で、「どこにストップが溜まっているか」を推測ではなく観測で得られる。

| | |
|---|---|
| 検証可能性 | **不可**。板のスナップショット履歴は自前で貯めない限り取得できない |

→ **Backtest Gate を通せない。** 導入するなら「今から記録を貯め始めて、半年後に検証する」
という別枠の扱いにする。`news_risk` がバックテスト再現不能で NEUTRAL 固定になっている
のと同じ立場のものを、もう1つ増やすことになる点は自覚しておく。

#### 2-5. オンチェーン指標 (取引所ネットフロー、MVRV、SOPR 等)

理屈は強い (長期の底値圏の識別力は実績がある) が、現実的な障壁が2つ:

- 有用なものはほぼ有料 (Glassnode / CryptoQuant)
- **時間軸が合わない**。日次〜週次の指標で、本戦略の4h足・21日期限という粒度に対して遅い

→ 4h足戦略の補強としては優先度低。**BTC/ETH の長期バイアス** としてなら意味がある。

### Tier 3 — モデルクラスの入れ替え

#### 3-1. GARCH / EWMA によるボラティリティ予測

現行の SL 幅は `2.5 × ATR(14)` = **過去14本の実現変動**。
だが SL に必要なのは「これから21日でどれだけ振れるか」という **予測** であって、
ATR は定義上それを持っていない。

GARCH(1,1) や EWMA はボラのクラスタリング (高ボラの後は高ボラ) をモデル化するので、
保有期間にわたるボラ予測を出せる。SL 幅、ポジションサイズ、期限日数のすべてが
これに乗る。

| | |
|---|---|
| 実装コスト | 中 (`arch` パッケージ追加 = `quant_core` の依存制約に触れる。要検討) |
| 検証可能性 | 高 |
| リスク | 効果が地味な可能性。ATR は粗いがロバスト。**先に「ATR の予測誤差がどれくらいか」を測ってから** 決めるべき |

#### 3-2. HMM / マルコフ状態転換によるレジーム判定

`_detect_regime` の `ATR%>3 → VOLATILE / ADX>25 → TRENDING / else SIDEWAYS` を、
隠れマルコフモデルによる確率的な状態推定に置き換える。
「TRENDING である確率 0.7」という連続量が出るので、Tier 1-1 の特徴量として直接使える。

| | |
|---|---|
| 実装コスト | 中〜大 |
| 検証可能性 | 高だが、**状態数の選択が事実上のハイパーパラメータ探索** = 多重検定問題に直結 |
| リスク | 高。W5 を先に解決していないと、「良いレジーム分割」を偶然見つけただけになる |

#### 3-3. 勾配ブースティング (LightGBM 等) + パージ付きウォークフォワード CV

Tier 1-1 のメタモデルを線形から非線形に上げる案。**標本数が揃ってから**。

金融時系列で通常の k-fold CV を使うと、ラベルの期間が重なる (21日バリア) ため
**訓練と検証に情報が漏れる**。パージ (purging) とエンバーゴ (embargo) が必須。

#### 3-4. 順応的予測 (Conformal Prediction) による区間出力

点予測 (BUY / NEUTRAL) ではなく、**カバレッジ保証つきの区間** を出す。
「21日後の R は 80% の確率で [-1.0, +2.0] に入る」という形。

分布を仮定しないので標本が少なくても保証が効く点が、この規模のデータに合っている。
副次的な利点として、Gemini の初心者向け要約に **不確実性を正直に書ける** ようになる
(現状の要約は点推定を断定的に述べる形になっている)。

---

### Tier 4 — 検証基盤 ★これが無いと上の全部が幻になる

**§0 で最優先に置いた理由がここ。**
Tier 1〜3 の改善は、すべて「バックテストで良くなった」ことを根拠に採否を決める。
その物差しが歪んでいる限り、どれだけ良い理論を足しても、選ばれるのは
**「歪みに最もよく適合した設定」** になる。

#### 4-1. 取引コスト (手数料・スリッページ・ファンディング)

現行バックテストにコストが一切ない (grep 済み)。

- Binance 現物 taker 0.1% ×2 (往復) = 0.2%
- 平均的な SL 幅が実効 ATR 2.5倍 (概ね 2.5〜10%) なので、
  **1R あたり 2〜8% のコストがかかっている計算**。期待値 -0.01R という数字は
  この分だけ良く出ている
- 加えて **EXPIRED = 0R は建値決済を仮定している**。実際には21日後の市場価格

期待値がゼロ近傍の戦略にとって、コストは誤差ではなく主要項。

#### 4-2. ウォークフォワード検証 / パージ + エンバーゴ

「学習期間で決めたパラメータを、見ていない期間で評価する」を強制する。
現行の `--compare` は全期間で両設定を評価して比べる形なので、
**パラメータ選択そのものが全期間を見て行われている**。

#### 4-3. 多重検定の補正

`--compare fixed-vs-atr` `--compare gate-vs-nogate` `--sl-mult` `--atr-cap-pct` …
と設定を変えて比較するたびに試行回数が増える。20通り試せば、真の優位性がゼロでも
1つは「有意に良い」設定が出る。

- Deflated Sharpe Ratio (試行回数を明示的に割り引く)
- PBO (Probability of Backtest Overfitting)

最小限でも **「これまでに何通り試したかをレポートに記録する」** だけで効果がある。
このリポジトリの流儀に合わせるなら、`logs/backtest/` の出力に試行カウンタを持たせて、
**比較表に必ず併記する** 形が自然。判定根拠をレポートに残さなかったせいで
ニュースゲートの誤爆に5ヶ月気付けなかった件と、同じ対処。

#### 4-4. ベンチマーク対比

「勝率 45%」が良いのか悪いのかは、単独では判断できない。

- バイ&ホールド (同期間・同銘柄)
- ランダムエントリー (同じ本数・同じ SL/TP ルール) を N 回

**ランダムエントリー対比は特に重要**。SL=2.5ATR / TP=2R / 21日期限という
出口ルール自体が、エントリーの質と無関係に一定の R 分布を生む。
現行の集計は「エントリーロジックの寄与」と「出口ルールの寄与」を分離できていない。

## 4. 推奨する順序と、その理由

```
Step 0  Tier 4-1 (コスト) + 4-4 (ランダムエントリー対比)
        ↓  ここで「そもそも優位性があるのか」が確定する
        ↓  もし優位性がゼロ〜負なら、Tier 2 で特徴量を足す前に
        ↓  エントリーロジックそのものの再設計を検討すべき、という分岐が立つ
Step 1  Tier 1-3 (Beta-Binomial) + 1-2 (キャリブレーション計測)
        ↓  小さく、既存構造にほぼ触らず、Kelly の暴れを止める
Step 2  Tier 4-2 (ウォークフォワード)
        ↓  ここまでで物差しが揃う
Step 3  Tier 1-1 (メタラベリング)
        ↓  ここが「予想の補強」の本体
Step 4  Tier 2-1 (ファンディング) → 2-3 (クロスセクション)
        ↓  メタモデルの特徴量として足す = 判定ロジックを書き換えずに済む
Step 5  Tier 1-4 (ボラ正規化) / Tier 3 (モデルクラス)
```

Step 0 を先頭に置いたのは、**分岐を作るため**。
コストを入れた結果が明確な負なら、Tier 1〜3 は「負の期待値をより正確に推定する作業」に
なってしまう。そこに工数を積む前に判断したい。

Step 4 が Step 3 の後なのは意図的。メタラベリング構造を先に作っておけば、
**新しい情報源は「特徴量を1列足す」だけで導入できる**。
逆順にすると、ファンディングを使うために `_decide_signal` の if/elif に
分岐を足すことになり、W1 (定数 confidence) を抱えたまま複雑度だけが上がる。

## 5. このリポジトリ固有の制約 (実装に入る前に必ず確認)

| 制約 | 内容 |
|---|---|
| **Backtest Gate** | `lib/quant_core.py` / `tools/tool_crypto.py` の変更は before/after 比較が必須。比較表をコミットメッセージに貼る。**Tier 4 を先に入れると、この比較表の情報量そのものが上がる** |
| **ロジックのフォーク禁止** | ライブとバックテストは `quant_core` の純関数を共有する。メタモデルの推論も**必ず共有層に置く**。ライブだけがモデルを使う形にしたら、Gate が意味を失う |
| **`quant_core` の依存制約** | pandas / pandas_ta のみ。`lib_shared` は APIキー無しで `sys.exit(1)` するので import できない。scikit-learn / arch を足すかは**設計判断として明示的に決める** (係数を定数で埋め込めば依存を増やさずに済む) |
| **`lib/paths.py`** | 新しいキャッシュ (ファンディング履歴、学習済みモデル) の置き場は `LOGS_DIR` 経由。絶対パスのリテラルを書いてよいのは `lib/paths.py` だけ (`verify_project.check_hardcoded_abs_paths()` が止める) |
| **コストガード** | 新しい外部データソースは `SWEEP_COUNTER` / `WATCHER_COUNTER` と同じ枠組みで日次上限を持たせる。Binance の公開 API は無料だが、レート制限はある |
| **naive datetime** | ファンディング/OI の履歴も epoch ms → UTC naive。trade_log は ローカル(JST) naive。**新しい時系列を足すたびにこの罠がある** (skill `crypto-backtest` 参照) |
| **先読み禁止** | 8時間ごとのファンディング、日次の OI を4h足に結合するときは、`backtest_crypto.py:100` の F&G と同じく「バー確定時点で公表済みの値」だけを使う |

## 6. 検討から外したもの (と、その理由)

| 候補 | 外した理由 |
|---|---|
| 深層学習 (LSTM / Transformer) による価格予測 | 標本数が桁違いに足りない。730日×4h足 = 約4,400本 ×3銘柄。トレード数に至っては数十件規模。この規模では過学習しか起きない |
| センチメント分析の高度化 (SNS / LLM による記事スコアリング) | 現行の `classify_news_risk` が誤爆で5ヶ月 trade_log をゼロにした事例がある領域。**バックテストで再現できない** (news_risk は NEUTRAL 固定) ため、改善したかどうかを測る手段が無い。測れないものを複雑にしない |
| ショート (売り) の追加 | 「価格予想の補強」ではなく戦略の別建て。SL/TP/Kelly の全経路を両方向に対応させる改修になり、範囲が違う |
| 他取引所への分散・アービトラージ | 予測ではなく執行の話 |
